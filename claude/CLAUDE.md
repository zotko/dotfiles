- Keep code comments concise; don't restate what the code already says. Match the comment style already used in the file/codebase (casing, tone, placement). Comments should be short, not verbose, don't go into fine details.
- Don't add comments explaining why a fix was made. The commit message has that context, the code should just be correct.
- Don't add a test plan section to PR descriptions.
- Never include anything referencing Claude or AI in PR descriptions, commit messages, issues, or comments: no session links, no co-authored-by trailers, no generated-with attribution or mentions of AI involvement.
- Keep PR summaries and comments short and direct, just the main points, no long explanations or background.
- When drafting messages (message, PR descriptions, review comments, etc.), keep them to 2 sentences max. This is a hard cap, it still applies when the logic involved is complex. Only the essentials, no details. Casual tone, shortnames (BQ, GCS, k8s, JS, TS, config, repo, db, auth, etc.), natural phrasing, not perfectly punctuated or capitalized. No markdown, backticks, bold, headers, or code blocks. Stay high level; avoid specific numbers and exact names. Don't put a period at the end of the last sentence.
- Temporary test scripts, one-off queries, and throwaway files go in `.local/` at the repo root (globally gitignored). Before creating a new test script, check `.local/` first, a relevant one may already exist.
- When you discover a project's CLAUDE.md is outdated or missing significant modules/architecture, proactively suggest updating it.
- Never use the em dash (—) in any output (drafts, responses, code comments, PR descriptions, etc.). Use commas, periods, parentheses, or colons instead.
- When creating a branch, base it on freshly-fetched origin/main (`git fetch` then `git switch -c <name> origin/main`), never on the current branch or a local main. Before reading code to plan work, make sure refs are current so you're not reasoning about stale state.
- When creating a ticket (Linear, GitHub issue, etc.), keep it concise and well structured. Just the problem, the ask, and any needed context. No padding with statistics, metrics, background sections, or exhaustive detail.
- When doing a code review, also read the existing review comments and discussion on the PR (if any) before writing your own, so feedback isn't duplicated and context from other reviewers is taken into account.
- Inline PR review comments: 2 sentences max, the issue and the ask. Keep the analysis out of the comment (no repro details, counts, measurements, or supporting evidence), that belongs in the chat.
